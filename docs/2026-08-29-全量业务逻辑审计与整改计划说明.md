# 2026-08-29 全量业务逻辑审计与整改计划说明

**审计日期：** 2026-08-29（北京时间）  
**审计范围：** Dashboard 菜单、前端请求编排、FastAPI 接口、数据库读取、训练/模型状态、系统巡检、线上服务和定时任务  
**审计方式：** 本地代码静态审计 + 线上只读日志/服务状态检查；未执行生产写入、数据删除、训练触发或交易操作  
**结论性质：** 当前整改基线，不代表任何工作包已验收

## 1. 执行结论

当前线上“菜单加载慢、长时间不显示、偶发超时”不是单个页面问题，而是**读请求图过密、重查询和诊断任务混用、状态接口级联、缓存边界不统一**共同造成的系统性问题。此前多次修补降低了部分接口的失败影响，但没有把读路径、后台任务和交易/训练业务边界彻底分开。

当前系统不适合宣称“所有菜单已稳定”，也不适合据此放开实盘。应先完成 P0 读链路隔离和服务资源治理，再推进训练、模型晋级和收益证据闭环。

## 6. 分阶段整改计划

### 阶段 0：事实冻结与可观测性（T+0 至 T+0.5 天）

1. 固化 Git commit、服务版本、配置摘要、模型注册表、数据库 schema 和最近 72 小时指标快照。
2. 保持 live 失败关闭；禁止通过页面刷新、审计或训练治理接口启动训练、回测、补历史仓位或下单。
3. 增加每个 Dashboard API 的 `request_id`、排队时间、查询耗时、响应字节、缓存命中、超时/降级原因。
4. 建立“真实 0 / 未知 / warming / partial / timeout / stale”统一状态枚举。

**验收：** 能按请求 ID 还原一次菜单点击触发的全部后端调用；不包含密钥和账户敏感信息。

### 阶段 1：读路径隔离与资源预算（P0，T+0.5 至 T+2 天）

1. 将轻量读、普通分页读、重聚合、系统审计分为独立并发池；重任务不能占满 Dashboard 全局槽位。
2. 移除持仓/每日盈亏/收益归因/模型贡献中的全量取回后内存切片，改为数据库分页、索引和增量聚合。
3. JSON 脱敏中间件改为按需处理并设置响应大小上限，禁止大列表一次性序列化两遍。
4. 所有只读接口返回 `checked_at`、`freshness`、`source`、`status` 和 `degraded_reason`。

**验收：** 任意菜单连续点击 20 次无请求风暴；首屏只读 P95 < 2 秒、P99 < 5 秒；单请求不超过 20 秒；内存峰值较当前 3.3 GB 明显下降并稳定在部署预算内。

### 阶段 2：审计、自检和监控合并（P0，T+1 至 T+3 天）

1. `/system/self-check` 仅执行轻量、可在 5 秒内完成的健康项。
2. `/system-audit/status` 只读最近快照；重审计由单独后台任务运行，设置总预算、取消、退避和 `deferred` 结果。
3. `/server-monitor/status`、自检和审计共享探针缓存，不重复 SSH、模型和数据库扫描。
4. 修复无结果帧、子进程退出和快照版本不一致时的结构化错误输出。

**验收：** 24 小时内无 150 秒审计超时；审计失败能在 5 秒内返回上一次快照加明确过期原因；交易服务不因审计请求出现资源饥饿。

### 阶段 3：前端请求图去重（P0，T+2 至 T+4 天）

1. 在 `dashboard.js` 建立页面级数据协调器，同一 endpoint 只允许一个刷新任务。
2. 菜单重复点击、模式切换、页面可见性恢复时取消旧请求，使用稳定 request key；移除 PnL/每日盈亏的 `Date.now()` 破坏去重行为。
3. 首屏只请求摘要和当前页必要数据；设置、训练、审计、服务器监控采用按页加载。
4. 训练页六个接口合并为统一观察快照，报告刷新改为显式按钮/后台任务。

**验收：** 浏览器网络面板中一次菜单操作的请求数有上限；切换模式不会刷新隐藏菜单；任何 503/超时不会触发立即并发重试。

### 阶段 4：交易事实、数据和训练治理闭环（P0/P1，T+3 至 T+7 天）

1. 统一订单、成交、仓位、保护单、手续费、资金费和结算的权威生命周期 ID。
2. 数据源按最近成功时间、失败原因、覆盖量和训练资格分层；异常样本隔离但不删除原始证据。
3. 训练样本使用当前纪元、时间切分和完整成本标签；明确 active/challenger/baseline 的样本边界。
4. 训练任务增加内存预估、单实例租约、最大重试 3 次、指数退避、熔断和恢复时间。

**验收：** 最近 24 小时无未归属成交、重复资金费、训练 MemoryError 和悬挂 run；训练报告能对齐样本游标、Artifact 版本和质量报告。

### 阶段 5：模型评估、专家贡献和晋级（P1，T+5 至 T+10 天）

1. 固定样本外窗口，对 active、challenger、无模型 baseline 做多空、逐币、市场状态和执行成本拆分。
2. 专家贡献只引用权威成交结果；未调用、超时、空响应、解析失败不能记为成功。
3. `live_ml_ready=true` 仅在费后收益、收益置信下界、Profit Factor、回撤、样本成熟度和时间滚动验证全部通过时写入。
4. 如果只有一侧或少数币种通过，只授权对应范围，不得整包晋级。

**验收：** challenger 样本和评估证据可追溯；模型注册表、调度状态、Artifact 指纹和页面显示一致；不以端口可达或模型数量代替训练效果。

### 阶段 6：连续观察与 Go/No-Go（T+10 至 T+13 天起算）

- **24 小时门槛：** 服务无非计划重启；Dashboard 无超时风暴；最大分析间隔 ≤ 180 秒；重复分析率为 0；数据采集分区无未解释超时；执行合同和对账新增异常为 0。
- **72 小时门槛：** 上述指标在三个自然周期内重复通过；模型隧道无未闭环 timeout/recovered；训练任务有明确完成或门禁阻断结论；收益归因等式逐笔平衡。
- **Go 条件：** P0 全部关闭，P1 有版本化证据，测试、部署和线上观察记录齐全。
- **No-Go 条件：** 任一 P0 重现、审计/数据采集再次出现无结果帧或持续超时、页面把未知显示成真实 0、或 live 门禁被绕过。
