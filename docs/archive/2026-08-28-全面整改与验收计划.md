## 1. 执行结论

当前系统**不具备恢复实盘交易或承诺稳定盈利的条件**。原因不是单一模型分数偏低，而是交易执行闸门、模型生产授权、训练调度、模型服务稳定性、Dashboard 重查询和测试契约同时存在风险。

当前必须坚持以下结论：

1. `can_open_new_entries=false` 或 OKX 对账状态为 `critical` 时，不得通过配置、页面按钮或人工脚本强制开仓。
2. `live_ml_ready=false` 时，模型不得影响 live 生产下单；paper 可以继续采样，但必须标注为模拟或观察数据。
3. 当前观察盈利不能证明模型盈利：约 `9347 USDT` 的观察净收益中，约 `10348 USDT` 来自资金费，而毛交易盈亏约 `-631 USDT`。
4. 当前 challenger 样本为 0，不能以“有 Artifact”“训练任务运行过”或“注册表有 15 个模型”替代候选模型证据。
5. 不承诺具体的“赚钱日期”。可以承诺的是整改阶段、验收门槛和每个阶段的最晚复核时间；是否放行取决于真实样本和连续运行证据。

### 2.2 分级定义

- **P0：交易或服务安全阻断。** 影响新开仓安全、订单事实完整性、核心服务存活、训练资源隔离或 Dashboard 可用性。P0 未关闭时不得进入 live 放行。
- **P1：质量和可持续性阻断。** 影响模型证据、收益归因、训练标签、连续观察或多空公平性。P1 未关闭时可以维护 paper，但不得宣称模型有效或晋级。
- **P2：展示、测试和运维改进。** 不直接决定交易安全，但必须在最终验收前完成，否则验收材料不完整。

## 3. 总目标和禁止事项

### 3.1 总目标

建立一个能够回答以下问题的系统：

1. 为什么本轮没有开仓，阻断发生在哪个阶段？
2. 页面显示的专家数、模型数、训练状态是否和后台事实一致？
3. 训练是否真正使用了完整、无未来泄漏、可追溯的真实标签？
4. 候选模型是否在费后、样本外、分多空和分市场状态的条件下优于 active 和无模型基线？
5. 线上服务在 24–72 小时内是否连续、可恢复、无重复任务和无隐性丢单？

### 3.2 禁止事项

- 禁止为增加开仓数量而降低 `production_trade_gate`、LCB、Profit Factor、资金费或风险门槛。
- 禁止把未调用、超时、空返回、解析失败或交叉验证缺失标记为 `completed`。
- 禁止把影子样本、反事实样本或预计资金费计入真实成交收益。
- 禁止在页面刷新、菜单切换或健康检查中隐式启动训练、回测、评估、下单或全量历史扫描。
- 禁止对失败训练无限重试；必须有幂等、退避、熔断和人工可审计的恢复动作。
- 禁止在 challenger 样本为 0、报告过期或数据指纹不一致时切换 active。
- 禁止删除异常资金费、异常成交或生命周期冲突记录；只能隔离并保留处理证据。

## 5. 分阶段整改计划

### 阶段 0：冻结、备份和事实基线（T+0 至 T+0.5 天）

**目标：** 防止整改期间状态继续漂移，并生成可回滚基线。

**动作：**

1. 记录当前 Git commit、服务版本、配置摘要、模型 Artifact 版本、注册表快照和数据库 schema 版本。
2. 继续保持 live 失败关闭；paper 仅保留必要采样，暂停会放大资源消耗的训练重试。
3. 生成最近 72 小时的只读基线：交易漏斗、OKX 对账、专家调用、训练状态、模型质量、Dashboard 接口耗时。
4. 保存当前线上配置和最近一次可启动版本，形成回滚包；回滚包不得包含 API key、私钥或账户敏感信息。

**验收证据：** `baseline_manifest.json`、服务状态快照、配置 hash、模型 registry 快照、回滚包校验值。

**停止条件：** 任何基线报告缺字段、时间范围不一致或包含写操作时，阶段不通过。

### 阶段 1：P0 交易执行合同和对账恢复（T+0.5 至 T+2 天）

**目标：** 让系统能够证明每一笔订单事实完整，并让新开仓权限只由真实对账状态决定。

**动作：**

1. 修复 `unresolved_trade_execution_contract` 的具体来源，逐笔核对 `order_id`、`inst_id`、`trade_id`、成交张数、成交价、手续费、资金费和生命周期。
2. 对同一 `posId` 的多个生命周期拆分归属，禁止跨生命周期合并资金费和收益。
3. 检查保护单覆盖、合约规格、名义价值、杠杆、余额和仓位快照的时间一致性。
4. 为对账任务设置只读扫描、增量窗口、明确超时和 `SKIP LOCKED` 等并发边界；禁止读任务持有交易写锁。
5. 只有以下条件同时成立，`can_open_new_entries` 才能恢复：未解决对账项为 0、关键交易心跳新鲜、执行合同违规为 0、保护单覆盖缺口为 0、服务连续运行通过。

**验收阈值：**

- 未解决、需人工复核、可修复关键项均为 0。
- 最近 24 小时新增执行合同违规为 0，未归属成交为 0，资金费重复归属为 0。
- 交易心跳年龄小于 120 秒；订单事实快速同步 P95 小于 30 秒。
- 不得因为“暂时没有机会”伪造开仓成功；没有合格机会时仍然记录 `no_candidate` 或对应阻断原因。

**失败处理：** 任何一项失败立即保持 `can_open_new_entries=false`，生成阻断报告并回滚本阶段变更，不清理历史异常。

### 阶段 2：P0 本地 ML 服务、训练调度和隧道治理（T+1 至 T+3 天）

**目标：** 解决“端口可访问但模型不可用”和 MemoryError 无限重试问题。

**动作：**

1. 为 8000、8002、8003、8101 建立区分“端口可达、健康、模型可推理、Artifact 可验证、生产授权”的五级健康状态。
2. 在训练任务前做内存预算、样本规模检查和并发上限；超过预算时返回结构化 `resource_blocked`，不得进入半运行状态。
3. 为每个 `local_ai` 工具模型增加单任务超时、最大重试次数、指数退避、熔断窗口和恢复探测。
4. `training_process_interrupted` 必须写入恢复时间和 `next_check_at`；重启恢复不能重复创建历史中断事件。
5. 隧道服务对 timeout/recovered 做限频告警，连续失败时停止新增推理请求，避免多次重启放大故障。
6. Artifact 生成、注册、激活和 `live_ml_ready` 必须使用同一版本指纹；只有评估证据通过才可授权。

**验收阈值：**

- 连续 24 小时无新的 MemoryError、未捕获的训练中断或无限重试。
- 同一 `run_id` 至多一个运行实例；失败任务最大重试次数有记录且不超过 3 次。
- 训练服务、模型隧道和推理服务无非计划重启；健康探测连续成功率不低于 99%。
- Artifact 可加载、版本 hash 一致、推理接口 P95 小于 5 秒；不可用时返回 `unavailable`，不伪装成“模型可用”。
- `live_ml_ready` 仍由模型晋级证据决定，服务恢复不等于模型自动晋级。

### 阶段 3：P0 分析调度、专家调用和候选池（T+2 至 T+4 天）

**目标：** 消除菜单点击卡死背后的重查询、重复分析、专家串栏和轮次空档。

**动作：**

1. 为每轮分析建立 `round_id`，为每个任务建立幂等键：`round_id + symbol + timeframe + analysis_type`。
2. 专家调用记录角色、请求 ID、币种、轮次、开始/结束时间、耗时、原始响应、解析状态和错误原因。
3. 统一状态枚举：`completed`、`timeout`、`parse_failed`、`empty`、`unavailable`、`skipped`；未调用不得计入成功数。
4. 必须区分配置专家数、本轮应调用数、实际调用数、成功数、失败数和跳过数；修复“4 个专家显示为 5 个”的展示契约。
5. 候选池去重、分层、轮换并记录入选/淘汰原因；同一幂等键只能保留一条有效记录。
6. 单专家独立超时，整轮设置总预算；单个专家超时不得拖死其他币种。
7. 将重查询改为后台缓存或分页增量读取；菜单点击只读取已有摘要，禁止触发全量历史审计。

**验收阈值：**

- 最近 24 小时重复分析率为 0；每个幂等键最多一条有效记录。
- P95 单轮分析耗时不超过 120 秒；最大分析间隔不超过 180 秒，超过即告警并记录原因。
- 每轮都能生成轮次总结；专家调用成功率、解析成功率、交叉验证完成率均可统计。
- Dashboard 首次加载和菜单切换的只读接口 P95 小于 2 秒、P99 小于 5 秒；任何单请求不得超过 20 秒。
- 页面请求超时只显示缓存和过期状态，不自动并发重试，不启动训练或审计任务。

### 阶段 4：P1 数据、资金费、收益和标签（T+3 至 T+6 天）

**目标：** 把“模型能力”和“资金费/执行偶然收益”分开，形成可信训练标签。

**统一公式：**

```text
费后净收益 = 毛盈亏 - 已发生手续费 - 可确认滑点 + 已结算资金费
```

**动作：**

1. 资金费拆成已结算值和预计值；预计值不得写入已实现收益或真实训练标签。
2. 每个样本必须关联：开仓、成交、持仓、资金费、平仓、手续费、滑点和最终结算。
3. 异常资金费、合约规格不一致、生命周期冲突和缺失账单样本进入 `excluded`，保留原始证据和处理理由。
4. 市场分析、持仓退出和训练分别展示资金费字段，不能重复计入同一笔资金费。
5. 训练特征只使用决策时已知数据；采用时间切分和滚动验证，禁止随机切分泄漏未来信息。
6. 分别计算多头、空头、币种、持仓时长和市场状态指标，确认 82.43% 多头集中是否来自数据、规则或真实市场分布。

**验收阈值：**

- 已结算资金费对账覆盖率 100%；重复归属和未归属均为 0。
- 收益组成等式逐样本和汇总层面均平衡，误差不超过账务精度容差。
- 真实训练样本完整生命周期覆盖率 100%；异常样本全部有隔离理由。
- 页面明确区分影子机会样本、反事实成本样本和 OKX 实际成交样本。

### 阶段 5：P1 模型评估、challenger 生成和晋级（T+5 至 T+10 天）

**目标：** 只在证据足够时决定保留、晋级或退回整改。

**动作：**

1. 冻结一份样本外数据，同时比较 active、challenger 和无模型 baseline。
2. 生成多空拆分、逐币留出、市场状态拆分、时间滚动和执行成本敏感性报告。
3. 独立评估方向、盈利质量、损失过滤、时间序列、情绪和退出专家，并做移除单专家的消融对照。
4. 候选模型必须绑定一个明确假设和输入指纹；输入不变时禁止重复训练。
5. `live_ml_ready=true` 只能在以下证据全部通过时写入：费后收益为正、收益 LCB 为正、Profit Factor 大于 1、回撤/尾部风险达标、样本成熟度达标、数据来源完整、时间滚动和市场状态验证通过。
6. 若仅某一方向或某些币种通过，只能限制授权范围，不能整包晋级。

**当前明确阻断：** challenger 样本为 0；本地 ML 多空收益置信下界不满足生产条件；做多 Profit Factor 约 `0.856`，做空点估计约 `1.385` 但收益下界仍为负。因此当前不得写入 `live_ml_ready=true`。

### 阶段 6：P2 Dashboard 重新排版和可观测性（T+4 至 T+9 天）

**目标：** 页面首先让人看懂事实和阻断原因，其次才展示图表。

**动作：**

1. 启动预热只做轻量健康检查和缓存读取；策略学习、数据采集、系统巡检改为后台任务和缓存报告。
2. 修复 `isolated system audit returned no result frame`，所有失败返回结构化 `partial`/`invalid`，不让前端等待空结果。
3. 将训练效果、模型数量、专家数量、开仓漏斗和收益组成放在明确的状态区；“15 个模型”必须显示为“注册表库存 15（可训练 8、推理/评估 7）”，不能显示为“同时训练 15 个”。
4. 页面只读接口统一使用请求去重、取消过期请求、固定返回上限和缓存新鲜度字段。
5. 训练效果页面只读取缓存报告，展示 active/challenger/baseline、费后收益、资金费归因、样本权威等级、专家贡献、执行漏斗和阻断原因。
6. 桌面、窄桌面和移动宽度均验证长模型名、空数据、负收益、0 样本和长错误原因不溢出。

**验收阈值：**

- 连续点击任意菜单 20 次，页面无卡死、无未处理 Promise、无请求风暴和无服务重启。
- 页面首屏只读接口 P95 小于 2 秒；无单次请求超过 20 秒；内存峰值较基线下降并稳定在平台预算内，具体预算由部署环境记录。
- 刷新和切换 Tab 不新增训练、评估、回测或交易 run。
- 报告状态为 `missing`、`partial`、`invalid` 或过期时，页面显示“结论不可用”，不得显示“训练成功”。

### 阶段 7：P1/P2 连续观察与最终放行（T+10 至 T+13 天起算）

**目标：** 用新部署窗口证明系统不是“刚重启时正常”。

观察分两层：

- **24 小时连续性观察：** 验证服务、分析、训练、Dashboard 和对账没有新的硬错误。
- **72 小时稳定性观察：** 验证 paper/影子样本、模型服务、收益归因和资源曲线在多个自然周期内稳定。

## 6. 24–72 小时线上观察门槛

### 6.1 24 小时必须全部满足

| 类别 | 通过条件 |
| --- | --- |
| 服务存活 | 交易、Dashboard、训练、模型隧道无非计划重启；心跳年龄小于 120 秒 |
| 对账 | 新增未解决交易合同项为 0；保护单覆盖缺口为 0；账单归属异常为 0 |
| 分析 | 轮次总结连续生成；最大分析间隔不超过 180 秒；重复分析率为 0 |
| 专家 | 应调用数、实际调用数、成功数和页面显示数一致；失败状态可解释 |
| 训练 | 无新的 MemoryError；失败任务有退避，不能无限重试；训练状态不悬挂 |
| Dashboard | 菜单点击 20 次无卡死；接口 P95/P99 达标；无请求风暴 |
| 数据 | 资金费、手续费、滑点和收益等式平衡；无未来数据泄漏告警 |
| 交易权限 | live 仍失败关闭；paper 权限不被模型未晋级错误关闭 |

### 6.2 72 小时必须全部满足

1. 上述 24 小时指标在至少三个自然运行周期内重复通过。
2. 模型服务 timeout/recovered 事件为 0，或每次均在定义的熔断和恢复窗口内闭环，不能只看端口可达。
3. 训练任务至少完成一次受控运行或明确证明“因样本/门禁没有启动”，两种情况均有报告，不允许状态悬挂。
4. 每日对账、训练心跳、模型 Artifact、Dashboard 缓存和交易日志的时间线可以互相对齐。
5. 观察收益按毛盈亏、手续费、滑点、资金费拆分；资金费贡献不能单独触发模型晋级。

观察期间任一 P0 事件发生，观察时钟归零，从修复后的新部署重新开始；P1 事件必须记录、隔离并经评审决定是否重置时钟。

## 7. Paper 和 Live 放行门槛

### 7.1 Paper 继续运行条件

- 执行合同、账户和合约规格检查正常；paper 不因模型尚未晋级而停止采样。
- 预测、门禁、订单模拟、持仓模拟和收益结算均写入完整事件链。
- 纸面收益和影子收益必须标注为非真实成交，不参与 live 盈利声明。
- 线上资源出现过载、分析间隔超过 180 秒或数据质量失效时，paper 自动降级为只读观察。

### 7.2 Live 生产放行条件

以下条件必须全部满足，缺一项即 No-Go：

1. 最近 72 小时观察全部通过，且最近 24 小时无 P0/P1 未关闭事件。
2. OKX 对账 `status=ok`，未解决项、人工复核关键项和执行合同违规均为 0。
3. `can_open_new_entries=true`，交易心跳新鲜，保护单覆盖完整。
4. 模型 Artifact 可复现、版本 hash 与 registry 一致，`live_ml_ready=true`。
5. challenger 在冻结样本外同时优于 active 和 baseline；费后收益、LCB、Profit Factor、回撤、尾部风险和稳定性均达标。
6. 真实成交样本达到当前模型合同要求；challenger 样本不得为 0。
7. 逐笔 `production_trade_gate`、账户、合约、成本和风控检查仍保留；模型授权不是逐笔下单许可。
8. 发布包、回滚包、监控告警和人工值班安排已经验证。

### 7.3 稳定盈利声明门槛

“可以交易”与“可以稳定赚钱”是两项不同验收。即使 live 通过，也不得仅凭 24–72 小时收益宣称稳定盈利。稳定盈利至少需要更长时间窗口、足够真实成交样本、费后正收益 LCB、跨市场状态稳定、回撤受控和资金费贡献不过度集中；具体样本数量由模型评审负责人在冻结数据合同中确认并版本化。

## 8. Go / No-Go 决策表

| 决策项 | Go 条件 | No-Go 条件 | 决策证据 |
| --- | --- | --- | --- |
| 服务发布 | 相关测试通过，回滚包可用，配置 hash 已记录 | 测试失败、配置漂移、无法回滚 | 发布检查单 |
| Dashboard 解锁 | 24 小时无卡死，P95/P99 达标，读接口无副作用 | 任一菜单点击卡死、请求风暴或内存失控 | 浏览器/接口压测报告 |
| 训练恢复 | 无 MemoryError，状态可恢复，重试有上限 | 无限重试、状态悬挂、资源超预算 | 训练运行报告 |
| Paper 采样 | 执行合同闭环，样本可归因 | 订单事实缺失、收益无法拆分 | 纸面交易链路报告 |
| Challenger 验收 | 样本外费后指标和稳定性全部达标 | challenger=0、LCB<=0、PF<=1 或数据不完整 | 模型评审报告 |
| Live 放行 | 72 小时观察通过且所有 live 条件满足 | 任一 P0/P1 未关闭或 `live_ml_ready=false` | Go/No-Go 签字单 |
| 稳定盈利结论 | 长期真实样本和风险证据均通过 | 仅有资金费贡献、短窗口或影子收益 | 收益证据报告 |

## 9. 自动关闸和回滚条件

以下任一条件发生，系统必须自动关闭新开仓或模型生产影响，并保留事件：

- OKX 对账出现新的关键未解决项、执行合同违规或保护单缺口。
- 交易心跳超过 120 秒，或连续两个分析周期没有有效轮次总结。
- 模型隧道连续超时达到熔断阈值，或 Artifact hash 与 registry 不一致。
- 训练进程出现 MemoryError、僵死、重复 run 或资源超过预算。
- 收益/资金费/手续费等式不平衡，或出现未来数据泄漏迹象。
- Dashboard 只读接口连续超时、出现请求风暴、内存峰值超过部署预算或产生任何写副作用。
- live 模型的 `live_ml_ready`、授权范围或版本状态在运行中变为未知。

回滚顺序：停止新增任务 -> 保留日志和快照 -> 关闭新开仓/模型影响 -> 恢复最近可验证版本 -> 运行只读对账和健康检查 -> 重新开始观察时钟。不得用回滚掩盖历史数据问题，也不得自动切换到未经验收的旧模型。

## 11. 部署、同步和验收流程

每次完成一个可发布代码变更后，严格执行：

1. 本地最小测试和静态检查。
2. 运行全量 pytest，记录通过/失败/跳过数量。
3. 运行线上同步：

```powershell
python scripts/sync_to_online_server.py --split-services
```

4. 部署后先做只读健康检查，再做 5 分钟 smoke；不直接下单、不切换 active。
5. 检查三项服务状态、模型隧道、OKX 对账、训练心跳、Dashboard 接口和日志错误。
6. 通过后开始 24 小时观察；24 小时通过后继续到 72 小时，不得把重启后的前几分钟当作稳定性证据。
7. 使用以下 Git 流程提交和推送：

```powershell
rtk git status --short
rtk git add <changed files>
rtk git commit -m "docs: add comprehensive remediation and acceptance plan"
rtk git push origin main
```

8. 每次重要变更完成后，将架构决定、验证结果、服务端口、观察门槛和已确认风险写入项目 `bb` Hindsight；不得写入密钥、私钥或临时猜测。

## 13. 预计时间和现实边界

在没有新增 P0 故障、线上资源足够且数据接口可用的前提下，工程整改可按 **10–13 个工作日**推进：前 3 天优先恢复服务和交易事实，接着 3–6 天完成标签与 Dashboard，5–10 天形成 challenger 评估，之后至少观察 24–72 小时再做放行决定。

这个时间表是工程交付窗口，不是盈利承诺。若真实成交样本不足、challenger 仍为 0、费后 LCB 不为正、Profit Factor 不达标或 72 小时观察失败，系统应继续 paper/影子运行并回到对应整改阶段，而不是为了赶日期开启实盘。

## 14. 当前结论（2026-08-28）

- **服务可用性：** 部分可用，但模型隧道、训练调度和 Dashboard 重查询仍未通过稳定性验收。
- **交易可用性：** paper 可作为观察环境；live 新开仓保持关闭，直到对账和执行合同恢复。
- **模型可用性：** Artifact 存在不等于生产授权；当前没有 `live_ml_ready=true` 的可放行证据。
- **训练有效性：** 当前 challenger 样本为 0，训练失败重试达到 12 次，不能宣称训练已改善模型。
- **盈利能力：** 观察净收益主要由资金费贡献，毛交易盈亏为负，不能宣称模型已经能够稳定赚钱。
- **下一步：** 先执行阶段 0–3 的 P0 任务，生成新的部署基线；只有 P0 通过后，才进入标签、模型晋级和 24–72 小时观察。
