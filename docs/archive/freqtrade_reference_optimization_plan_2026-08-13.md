# BB 系统借鉴 Freqtrade 优化方案

> 日期：2026-08-17（首次编制：2026-08-13）
> 文档性质：架构与实施建议，不代表已实施，不要求引入 Freqtrade 作为生产交易框架。

## 1. 文档目的

本方案用于整理 Freqtrade 对 BB 当前量化交易系统可借鉴的工程能力，并把这些能力转化为适合现有系统的优化路线。

核心结论：**不使用 Freqtrade 替换 BB，也不在生产环境引入第二套交易主循环；选择性借鉴其策略规范、实验管理、参数优化、交易保护、候选池和可复现性设计。**

BB 已经具备 AI 多专家决策、模型训练与晋升、Backtrader 回测、paper/live 分级权限、OKX 权威事实同步、收益门禁等能力，系统边界和业务复杂度高于通用交易机器人。Freqtrade 更适合作为工程设计参考、实验基准和必要时的旁路验证工具。

## 2. 方案边界

### 2.1 本方案要解决的问题

- 降低回测、paper 和 live 三种环境之间的策略语义漂移。
- 统一策略、参数、数据、成本和执行假设，使实验可复现、可比较。
- 为参数搜索增加时间序列验证和防过拟合约束。
- 将分散的交易保护与候选币过滤规则收敛为可配置、可观测的机制。
- 把策略/模型晋升需要的证据统一到一条可审计链路。
- 让拒单、拦截、降级和配置变化在 Dashboard 中可以快速定位。

### 2.2 明确不做的事情

- 不用 Freqtrade 替换现有 `services/trading_service.py` 生产编排。
- 不引入第二套生产订单状态机或第二个订单事实来源。
- 不让 Freqtrade 直接管理 OKX 实盘账户、仓位和资金。
- 不用 Freqtrade 数据库替代 PostgreSQL、Redis 或 OKX 权威结算事实。
- 不迁移现有 AI 多专家、模型训练、收益门禁和 paper/live 权限体系。
- 不以胜率作为参数优化或策略晋升的主要目标。

## 3. Freqtrade 已有能力概览

| CLI 任务体系 | 将回测、优化、数据检查等操作规范为独立命令 | 高，可提升运维一致性 |

## 4. BB 当前能力与差距

### 4.1 已具备且应继续保留的能力

- `backtest/engine.py`：基于 Backtrader 的现有回测能力。
- `executor/paper_executor.py`：paper 交易执行与状态管理。
- `services/trading_service.py`：生产交易编排、风险检查和执行入口。
- `services/okx_order_fact_sync.py`：交易所订单事实同步与权威状态校正。
- `services/strategy_learning.py`：策略学习、历史回放和绩效反馈。
- `services/position_execution_persistence.py`：持仓执行相关持久化。
- `core/trading_mode.py`：shadow、paper、live 等运行权限边界。
- PostgreSQL/Redis：业务持久化、状态和缓存基础设施。
- 模型晋升、收益门禁、生产许可和 Dashboard 监控体系。
- systemd 服务和定时器组成的线上运行与任务调度体系。

### 4.2 需要重点优化的差距

1. **运行语义一致性不足**  
   同一个策略在历史回测、实时 paper、生产 live 中可能经过不同的数据整理、信号确认、成交成本和执行规则，导致结果不可直接比较。

2. **实验合同不够完整**  
   策略版本、代码提交、数据版本、参数、手续费、滑点、随机种子和运行环境尚未形成统一实验快照。

3. **参数优化容易失真**  
   如果只在单一历史区间追求胜率或毛收益，会产生过拟合，且无法反映手续费、滑点、资金容量与尾部风险。

4. **保护与候选池规则分散**  
   冷却、连续亏损、回撤、流动性、点差和币种质量等规则分布在不同环节，难以统一配置、解释和复盘。

5. **拒单链路诊断成本较高**  
   信号可能依次经过模型权限、收益门禁、风险、余额、仓位、交易所约束等多个检查。最终结果存在，但“为什么未交易”的证据不够集中。

6. **晋升证据碎片化**  
   回测、shadow、paper、收益完整性、风险和生产许可数据需要汇总为同一份晋升材料。

7. **配置变更审计与回滚需加强**  
   生产参数变化必须能回答谁在何时修改、影响哪些策略、运行使用哪个版本，以及如何恢复上一有效版本。

## 6. 目标设计

### 6.1 统一策略合同

建议将策略的纯决策与交易执行彻底分开。策略只接收已经对齐时间的输入，不直接访问交易所、不直接写订单状态，也不自行修改生产配置。

建议的概念接口：

```text
StrategyContext
  market_snapshot
  feature_snapshot
  position_snapshot
  account_constraints
  decision_time
  mode
  parameter_set

StrategyDecision
  action: enter | exit | hold | reduce
  side
  target_exposure
  confidence
  reason_codes
  protection_hints
  strategy_version
  parameter_version
```

同一 `StrategyContext` 在 backtest、paper、live 中必须得到同一个 `StrategyDecision`。三种模式的差异应限制在执行适配器，例如撮合、延迟、滑点、订单确认和交易所错误处理。

### 6.2 统一实验合同

每次回测、参数搜索、历史回放或晋升评估都应生成唯一实验 ID，并至少保存：

- 策略 ID、策略版本、模型版本和 Git commit。
- 参数集合及其内容摘要。
- 数据集 ID、交易对、K 线周期、起止时间、时区和数据校验值。
- 训练、验证、样本外窗口的划分规则。
- 手续费、资金费、滑点、延迟、最小下单量和成交假设。
- 初始资金、仓位上限、并发仓位数和复利方式。
- 随机种子、依赖版本和运行器版本。
- 收益、回撤、风险、交易分布和数据质量指标。
- 结果状态、失败原因、产物路径和创建时间。

实验配置一旦运行不得原地修改；任何变化都创建新的实验和配置版本。

### 6.3 参数搜索目标

参数搜索不建议直接照搬 Freqtrade 默认损失函数。BB 的目标函数应以真实可结算收益为中心，例如：

```text
score =
    fee_adjusted_net_profit
  + profit_factor_reward
  + cross_window_stability_reward
  - max_drawdown_penalty
  - tail_loss_penalty
  - turnover_and_cost_penalty
  - instability_penalty
  - insufficient_sample_penalty
```

必须设置硬约束：

- 样本外费后净收益为正。
- Profit Factor 达到项目规定门槛。
- 最大回撤和尾部单笔损失不超过风险上限。
- 最小交易样本量满足统计要求。
- 不同市场阶段不能只有单个窗口获利。
- 参数小幅扰动后结果不能出现断崖式恶化。
- 未通过收益完整性与 OKX 事实口径校验的结果不得晋升。

### 6.4 Walk-forward 验证

建议按时间顺序执行，禁止随机打乱时间序列：

1. 在训练窗口搜索候选参数。
2. 在紧邻的验证窗口筛除过拟合候选。
3. 在从未参与搜索的样本外窗口评估。
4. 将窗口向前滚动并重复以上过程。
5. 汇总每个窗口的费后收益、回撤、Profit Factor、尾部损失和参数稳定性。
6. 最终候选先进入 shadow，再进入 paper；满足观察期和最小成交样本后才可申请 live。

### 6.5 Protection 规则链

建议按固定顺序运行，并为每个规则输出标准原因码：

| 保护规则 | 触发依据 | 默认动作 | 解除条件 |
| --- | --- | --- | --- |
| Cooldown | 刚完成交易或异常退出 | 暂停该币种新开仓 | 冷却时间结束 |
| Consecutive Loss | 连续亏损达到阈值 | 锁定策略或币种 | 时间到期并通过复核 |
| Max Drawdown | 滚动窗口回撤超限 | 降低风险或停止新开仓 | 回撤恢复并满足恢复门槛 |
| Low Profit Pair | 币种在足够样本下费后收益过低 | 暂时移出候选池 | 新窗口评估通过 |
| Spread/Liquidity | 点差或深度不满足要求 | 拒绝当前交易 | 市场质量恢复 |
| Exchange Health | 行情、时钟、API 或事实同步异常 | 停止新增风险 | 健康检查恢复 |

保护状态必须带作用范围、开始时间、到期时间、阈值、观测值、来源事件和人工解除记录。人工解除不能删除原始触发证据。

### 6.6 候选池过滤链

建议将候选交易对生成过程设计为有序过滤链：

1. 交易所可交易状态与项目白名单。
2. 稳定币、杠杆代币和明确黑名单排除。
3. 最低上市时间与历史数据完整性。
4. 24 小时成交额、盘口深度和点差过滤。
5. 价格、最小下单量与账户规模适配。
6. 波动率和异常行情过滤。
7. 策略适用性与近期费后表现过滤。
8. Protection 锁定状态过滤。

每个过滤器应记录输入数量、输出数量和被移除对象的原因，使某币种“为什么没有参与交易”可以直接查询。

### 6.7 统一交易生命周期与原因码

建议统一以下阶段，但继续以 OKX 返回和同步结果作为实盘订单、成交、手续费和结算的权威事实：

```text
candidate
  -> signal_generated
  -> signal_rejected | risk_approved
  -> execution_requested
  -> order_submitted | submission_failed
  -> partially_filled | filled | cancelled | rejected
  -> position_opened
  -> exit_requested
  -> position_closed
  -> exchange_reconciled
  -> profit_finalized
```

原因码建议按命名空间管理，例如：

- `SIGNAL_*`：策略未产生或主动撤销信号。
- `MODEL_*`：模型权限、置信度或版本问题。
- `PROFIT_GATE_*`：收益门禁未通过。
- `RISK_*`：风险、敞口、回撤或 Protection 拦截。
- `MARKET_*`：流动性、点差、行情新鲜度或候选池问题。
- `ACCOUNT_*`：余额、仓位、保证金或模式限制。
- `EXCHANGE_*`：交易所校验、拒单、限频或不可用。
- `RECONCILIATION_*`：本地状态与 OKX 权威事实不一致。

## 7. 分阶段实施计划

### P0：建立基线与实验合同

目标：先解决“当前运行的到底是什么，以及结果能否复现”。

- 盘点策略、模型、参数、数据和成本口径。
- 定义策略版本、参数版本、数据集版本和实验 ID。
- 定义统一实验配置与结果 schema。
- 为现有关键策略补录一组不可变基线实验。
- 明确 OKX 权威事实与历史回测数据的对账口径。

交付物：实验合同、版本规范、基线结果、差异清单。  
完成标准：任选一个基线实验可根据记录完整重跑，核心指标在容差内一致。

### P1：统一回测、paper、live 策略语义

目标：让三种环境共享决策输入、策略逻辑和原因码。

- 定义 `StrategyContext` 与 `StrategyDecision`。
- 建立历史行情和实时行情到统一快照的适配。
- 将成本、滑点、延迟和成交规则显式化。
- 增加同快照决策一致性测试。
- 增加未来函数和递归指标检查。

交付物：策略合同、适配规则、一致性测试报告。  
完成标准：相同快照的策略决策一致；差异仅来自有记录的执行假设。

### P2：参数搜索与防过拟合

目标：提高搜索效率，同时保证候选具有样本外泛化能力。

- 建立可声明的参数空间和约束。
- 实现可中断、可恢复、可审计的离线搜索任务。
- 实施 walk-forward 与样本外验证。
- 使用费后收益、Profit Factor、回撤、尾部损失和稳定性综合目标。
- 加入参数扰动和市场阶段稳定性检查。

交付物：搜索任务规范、目标函数、验证报告模板。  
完成标准：所有晋升候选都有样本外结果，且不存在只靠胜率或单区间成绩晋升。

### P3：Protection、候选池与诊断统一

目标：让保护和过滤行为配置集中、证据完整、状态可见。

- 建立 Protection 规则链与状态生命周期。
- 建立候选池过滤器接口和执行顺序。
- 统一交易全链路原因码。

## 11. 风险与回滚原则

- **影子接入优先**：新合同、原因码或保护规则先只记录不拦截，对比现有行为后再启用。
- **单变量推进**：每次只启用一类规则或一组明确关联的变化，避免收益变化无法归因。
- **保持唯一事实源**：不得因实验注册或旁路工具改变 OKX 权威订单与结算边界。
- **禁止自动直升 live**：参数搜索结果只能生成候选，不能绕过 shadow、paper、收益门禁和人工审批。
- **向后兼容**：新实验字段和原因码上线期间允许读取历史记录，但不能伪造缺失证据。
- **可撤销**：每个 Protection、候选池过滤器和新配置都必须有独立开关及上一有效版本。
- **先验证再扩面**：从少量策略、少量交易对和固定窗口开始，验证后逐步扩大。

## 12. 是否需要本地运行 Freqtrade

实施本方案并不要求本地常驻运行 Freqtrade。建议按以下顺序使用：

1. 首选阅读其公开设计和测试方式，将成熟模式实现到 BB 现有边界内。
2. 对回测或参数搜索结果存在疑问时，可临时将标准化数据和简单策略放入 Freqtrade 做旁路对照。
3. 对照结果只作为诊断证据，不直接进入生产订单和收益事实链。
4. 验证完成后可停止或删除临时环境，不增加长期运维负担。

如需本地旁路验证，常规开发电脑一般可以运行基础回测与小规模 Hyperopt；大规模多币种、多时间周期和高并发搜索主要受 CPU 核心数、内存和历史数据量影响。它不是本方案的前置条件。

## 13. 推荐执行顺序

建议依次执行：

1. 统一实验合同和基线。
2. 统一策略决策语义。
3. 补齐未来函数、递归偏差和数据质量检查。
4. 建立 walk-forward 参数搜索。
5. 收敛 Protection、候选池和原因码。
6. 建立实验注册表、晋升证据和配置治理。

这一顺序先解决可信度和可复现性，再提高搜索效率，最后完善自动保护与治理。若先大规模调参而未统一数据、成本和执行口径，得到的最优参数没有可靠的生产意义。

## 14. 最终结论

Freqtrade 对 BB 最有价值的不是其交易机器人本身，而是成熟的策略规范、实验工具、参数搜索、时间序列验证、Protection、Pairlist 和运行可观测性。

BB 应保留现有 AI 决策、回测、paper/live 权限、OKX 执行与权威结算体系，以“统一合同、统一证据、统一原因码”为主线吸收这些能力。完成后预期可以降低回测与实盘偏差、减少无效调参、加快未交易问题定位，并让每个策略从实验到实盘的晋升决定真正可复现、可解释、可回退。
